An MCP gateway sits between AI agents and MCP servers and decides each tool call: who may call which tool, how often, whether a person approves it first, and with which credential. Quilzo is one for its own agents, and offers the same to other vendors' agents at /mcp/gateway/NAME.

Declare a tool server

  1. Write the declaration

    Declarations live in integrations.json in the store. Each names one host, why this install reaches it, and the tools it may call there. Everything is off until somebody turns it on, so an example pasted from somewhere does nothing by accident.

    {
  "declared": [
    {
      "name": "tracker",
      "kind": "mcp",
      "enabled": true,
      "purpose": "File and read issues in the support tracker",
      "endpoint": "tracker.example.com",
      "uses": ["list_issues", "create_issue"],
      "writes": true,
      "secret": "tracker-token"
    }
  ]
}
    FieldMeans
    endpointExactly one hostname: no scheme, no path, no wildcard. Quilzo always uses https.
    usesThe tools this install may call there. Never "everything the server offers": a server can add or redefine a tool after the day you trusted it.
    writesThe tools change something on the far side, so a reviewer does not have to guess from their names.
    secretThe name of the credential. Its value is read from QUILZO_SECRET_TRACKER_TOKEN (the name in capitals, with anything else turned into _), never from the store, because the store keeps history that cannot be deleted.
    quilzo integrations list
    tracker  mcp  enabled
  File and read issues in the support tracker
  reaches tracker.example.com
  may call list_issues, create_issue
  changes something on the far side

  2. Look at what the server offers, and pin it

    quilzo integrations tools tracker asks the server what it offers and marks what you agreed to. The difference between the two lists is worth reading. When you are satisfied, pin the tools: Quilzo records a SHA-256 of each tool's definition (name, description and input schema) as the server gave it that day.

    quilzo integrations tools tracker
quilzo integrations pin tracker list_issues create_issue

    A pinned tool whose definition later changes is refused until a person pins it again, and the shield is told. This is the answer to tool poisoning: a name staying the same is not the tool staying the same. Only a pinned tool can be chosen by a model.

  3. Check it in the admin

    Administration › Integrations shows each server, what it may call, how it authenticates, and whether it is offered through the gateway.

Let an agent use a tool

An agent names each tool it needs, on its host, with a purpose, in its declaration. Tools that change something can ask first:

"tools": [
  { "name": "list_issues", "host": "tracker.example.com", "purpose": "see whether a problem is already reported" },
  { "name": "create_issue", "host": "tracker.example.com", "purpose": "report a problem it finds", "writes": true }
],
"ask_first": ["create_issue"]

A call is allowed only if the agent declares the tool, an enabled integration offers it, and it is pinned. Every call is recorded, and the exfiltration breaker stops a call when the run holds something private and has read somebody else's words (see Limits that hold). Try a call by hand with quilzo integrations call tracker list_issues.

Public addresses only, for now. The client refuses loopback and private network addresses, as protection against a declaration being pointed at internal services. A tool server on your private network cannot be declared yet.

Offer your MCP servers to other agents

Another vendor's agent, or one your teams built, can reach a declared server through Quilzo instead of directly. It gets only the pinned tools, at the role and daily limit you set, with Quilzo's credential injected and never its own. Every call is checked, counted and recorded with a digest of its arguments.

  1. Turn the gateway on for one server

    quilzo integrations gateway tracker --role author --daily 200 --ask create_issue

    --role is the least role a caller needs (reader, author or publisher). --daily caps one caller's calls a day (500 if you name none). --ask lists tools a person approves call by call. --off stops offering it.

  2. Give the caller the address and a token

    The server is offered at https://YOUR-ADMIN/mcp/gateway/tracker. A caller authenticates with a Quilzo token or an OAuth connection (see Connect AI apps), and is limited by that principal's access.

  3. Decide the calls that wait

    A call to a tool under --ask waits under Calls waiting for a person. Approved, exactly that call goes through once, within the hour. Somebody other than the person it acts for must decide.

    quilzo integrations held
quilzo integrations approve gq_915959844d12
quilzo integrations decline gq_915959844d12

Every caller of the gateway, and every tool server, also appears on the Fleet map.

Tell other systems when something happens

A webhook is a signed POST to a URL you choose when something is published, rolled-back, scheduled, submitted (a form) or proposed (a change waiting for approval). Only https endpoints are accepted.

quilzo webhook add https://deploy.example.com/hooks/quilzo

The signing key is printed once. Each delivery carries X-Quilzo-Event, X-Quilzo-Delivery, X-Quilzo-Timestamp and X-Quilzo-Signature. The signature is an HMAC-SHA256 over the timestamp and the body, each prefixed with its length, so the boundary between them cannot be moved. Reject anything more than five minutes old. A receiver in Python:

import hmac, hashlib, struct, time

def verify(key, timestamp, body, signature, now=None):
    if abs((now or time.time()) - int(timestamp)) > 300:
        return False                      # too old or from the future: a replay
    mac = hmac.new(key.encode(), digestmod=hashlib.sha256)
    for field in (timestamp.encode(), body):
        mac.update(struct.pack(">Q", len(field)) + field)
    return hmac.compare_digest("v1=" + mac.hexdigest(), signature)

quilzo webhook list, webhook test and webhook remove ID manage them.

Traces and the audit log, to your own tools

Set telemetry.otlp_endpoint and every agent run is sent as OpenTelemetry spans using the GenAI semantic conventions (gen_ai.operation.name, gen_ai.tool.name and the rest) to the collector you already run.

The audit log exports to a SIEM as OCSF (the default), CEF or JSON Lines. --envelope writes every exported event's hash, in order, beside the export, so the receiving side can tell whether anything was added, removed or reordered:

quilzo siem ocsf --envelope envelope.json > audit.ocsf.jsonl
quilzo siem jsonl --envelope evidence.json > audit.jsonl
quilzo siem verify audit.jsonl --envelope evidence.json
verified  185 event(s), sequences 1-185
  nothing was added, removed, reordered or altered since export

An OCSF or CEF record carries its event's hash (metadata.uid, or cs3 in CEF) rather than the whole event, so compare those with the envelope. A JSON Lines export carries each event whole, which is what siem verify recomputes; keep one of those as evidence.
