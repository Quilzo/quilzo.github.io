A feature is one file that declares the blocks a piece of work needs: content types, collections of records, listings, forms, pages, menus, chatbots, agents and webhooks. Quilzo checks every block by the same rules it holds that block to anywhere else, shows what the whole can do in plain words, and installs it as one decision.

What a package declares

Start from a complete example, a lab sample tracker, and edit it:

quilzo feature example > lab.json
quilzo feature check lab.json      # what it would store, show, send and change; installs nothing
BlockBecomes
typesContent types, flat lists of fields (see Types)
collectionsCollections of records bound to one of the package's types
listingsDeclared queries over those records that a page can show (see Structure)
formsForms with their purpose, lawful basis, notice and retention (see Forms)
pagesPages, added to the draft and never published by the install
menusMenus whose entries point at pages that exist
chatbotsChatbots answering from published pages (see Chatbots)
agentsAgent declarations, answered for by the person who installs them (see Agents)
webhooksEndpoints told about events; each gets its signing secret at install, shown once

A package has a name, a version, a title and a purpose, and a key it does not know is refused rather than ignored. It carries no code, no secrets and no access grants.

The permission card

The card is worked out from the package, never from its author's description: which records it keeps and whether their fields are about people, what its forms collect and for how long, which pages show what and to whom, what it sends and where, and what each agent may do, where it reaches and whether it asks first.

One administrator installs a feature that stores and shows ordinary content. Two different administrators must agree when it:

  • stores personal data, such as an email address, a name or a phone number;
  • stores what looks like health, belief or other special-category data;
  • collects what visitors type into a form;
  • lists records about people on a public page;
  • sends events or calls to another server;
  • adds an agent that acts without asking first.

A model may draft a package. Only a person installs or approves one.

Install, approve, roll back, remove

ToRun
Install, or ask for a second personquilzo feature install lab.json
See what is waitingquilzo feature pending, or Approvals
Approve or decline, as somebody elsequilzo feature approve ID, quilzo feature decline ID
List and read what is installedquilzo feature list, quilzo feature show NAME
Go back to the previous versionquilzo feature rollback NAME
Take everything it made backquilzo feature remove NAME

In the admin, Make takes a package file or pasted text, shows its card and every change it would make, and installs exactly what you read: the bytes are checked against the digest you were shown.

A feature owns what it made and nothing else. A block somebody made by hand, or another feature made, with a name the package also uses is a conflict, and nothing is installed. An upgrade changes what changed and removes what the new version no longer declares. Removing a feature stages the removal of its pages in the draft and keeps the records people entered.

Share a feature

Export an installed feature signed with your installation's log keys, Ed25519 and ML-DSA, and whoever installs it checks the signature against your published keys:

quilzo feature export lab-samples --sign -o lab.json
quilzo feature install lab.json --keys head.pub.json

A signed package is refused unless its signature is checked. To package something already built by hand, name its blocks:

quilzo feature capture inventory --title "Inventory" --purpose "What the lab holds" \
  --type sample --collection samples --listing available_samples --page samples -o inventory.json
