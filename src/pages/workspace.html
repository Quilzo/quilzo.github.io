An agent's workspace is a folder of its own, kept between runs. The agent never holds a shell. It names a program it was given and the arguments, and Quilzo runs that one command in a fresh box against the workspace. Nothing it writes is ever handed to a shell to interpret, unless you name a shell as one of its programs. Its files are read and written by Quilzo itself, through a handle on the workspace that cannot be walked out of.

Declare what it may run

{
  "name": "site-keeper",
  "kind": "task",
  "purpose": "Keep the site's repository tidy and its tests passing",
  "capabilities": ["file_list", "file_read", "file_write", "shell_run"],
  "autonomy": "draft",
  "shell": {
    "programs": ["git", "go", "make", "ls", "grep"],
    "hosts": ["proxy.golang.org", "github.com"],
    "ask": ["network"],
    "timeout": "2m", "memory_mb": 2048, "quota_mb": 2048
  },
  "budget": {"steps": 40, "tool_calls": 1, "duration": "20m"}
}
FieldWhat it allows
programsThe only programs it may run, by name. Each is found on the box's own path and run with the arguments exactly as given: no shell, so nothing in an argument is ever a command. code_run runs code with one of them, so an agent holding it names an interpreter here.
hostsWhat a command that reaches the network may reach, through the run's proxy, on 443. None means no command reaches the network at all.
askWhich kinds of command wait for a person: network (the default) and write. A command that deletes or rewrites history always waits.
workspaceThe folder. Empty means one of its own beside the store's other folders. You may name another, as long as it is not the store, a folder holding the store, or a system folder.
timeout, memory_mb, quota_mbEach command's time and memory, and the workspace's size. A workspace over its quota takes no more writes until something is removed.

What the agent can do

ActionWhat it does
file_listLists a folder in the workspace: names, sizes and kinds.
file_readReads a file's text, up to 256 KB, or a range of its lines from a file of up to 64 MB. A binary file is described, not shown.
file_searchFinds files by name, or lines by text or a regular expression, under a folder. It answers with at most 200, and says when it stopped before looking everywhere.
file_writeWrites a file whole (up to 1 MB), making the folders it needs, and says what changed.
file_editReplaces exact text that is in the file once (or every time it is), or inserts text after a line.
file_moveRenames or moves a file or folder. What was at the new name goes to the bin first, and the answer says so.
file_deleteMoves a file or folder into the workspace's bin, where it is kept a week and file_move brings it back. Deleting from the bin is for good, so that waits for a person.
shell_runRuns one program with its arguments, and gives back the exit status, the start and end of what it printed, how long it took and which files it changed.
code_runRuns code in Python, JavaScript, TypeScript, shell, Ruby, Perl, PHP or Lua, with an interpreter the declaration names (python3, node, deno, sh, ruby and the like), and gives back what it printed.

code_run reads the workspace and changes nothing, unless the code says it writes. Code that writes may change or delete anything there, so a person reads it whole and approves it first; it is at most 8 KB, and anything longer is written to a file and run with shell_run. Code never reaches the network. With write in ask, writing, editing, moving and deleting into the bin wait for a person too.

A file is written where its name says: never through a link, and never inside git's own folder, where a configured hook would be a program git runs later. Reading the workspace, listing it, searching it, or what a command or code printed, taints the run. A repository cloned or a file a page gave may hold somebody else's words, so the run is treated like one that read stored content.

What each command is

Every command is classed before it runs, from the program and its arguments, without guessing at intent. A program not known is taken as writing.

KindExamplesWaits for a person
readsls, cat, grep, git status, git log, go vetnever
writesgit commit, go build, go test, make, sed -i, anything unknownwhen ask has write
reaches the networkgit fetch, git push, go mod download, npm install, curlwhen ask has network
destroysrm, git reset, git clean -f, git push --force, find -delete, and any shell, which can do anythingalways

The kind is enforced as well as asked about. Only a command classed as reaching the network is given a way out, so go test runs with no network at all. A command classed as reading gets the workspace read-only, so whatever it runs in turn (a repository's configured hook, a search tool's preprocessor) cannot change it either.

One limit to know: a program that runs other code, such as a build, a script or a test suite, is writing, and that code can delete what the command may write. "Destroys" catches the commands that say so. To approve every change, add write to ask, or keep the workspace in git, so nothing written is lost. If the run holds something private and has read somebody else's words, a command that reaches the network also carries the breaker's reason when it asks. What a run writes into the workspace after reading something private stays private to the next run on it.

How a command runs

  • A fresh box for each command, the same one programs and the browser run in: its own namespaces, Landlock, the system call filter, no capabilities, and no way to reach a socket on the machine's filesystem. It may write only the workspace and the run's scratch home. It reads the system's programs and libraries, and nothing of the store. A command starts in well under a tenth of a second.
  • A home made fresh for each run, and removed when the run ends, so nothing a command leaves there (a configuration, a startup file) reaches the next run. The agent's caches (Go modules and builds, npm, pip) are kept between runs, and only a command that writes may write them. A command that only reads gets a home of its own, removed after it.
  • No prompts. Its input is empty, except the code code_run gives its interpreter, and its environment says CI=1, with no pager and no colour. A program that would ask a question gets nothing rather than waiting. Both of its output streams are captured together.
  • Nothing outlives it. When the command ends, everything it started ends with it. The time limit, Stop the run and the run's budget all end it the same way.
  • One run at a time works on a workspace; another is told which run has it.
  • The quota holds while a command runs. The workspace and the run's home are measured every few seconds, and a command that goes over is stopped. Memory is bounded per process, and each command may start at most 512, so one command can still use a good share of a small machine.

What is kept, and what a person sees

  • Each step's record in the signed log names the command, and has the SHA-256 digest of everything it printed and its exit status. The output itself (up to 1 MB) is kept with the run, sealed when the store has a keyring, and pruned with the run.
  • The run's page shows each command with its result, a link to the whole output, and which files it changed. A held command shows exactly what would run and why it is held: Let it go ahead or Decline, there or with quilzo agent approve RUN STEP.
  • Running with less, it only reads. A read-only token, an agent held to proposing, and every evaluation get only the commands that read. Nothing is written.
quilzo agent workspace site-keeper
quilzo agent workspace site-keeper --clear

The first says where the workspace is and how big. --clear empties it, with its caches, and the log records who did.

Read the web without a browser

To read a page or search the web, a browser is more than an agent needs. web_fetch reads an https address and gives back its words and links, without its scripts, styles and forms; text and JSON are read as they are. web_search asks a search provider and gives back what it found.

"capabilities": ["web_fetch", "web_search"],
"web": { "fetch": ["docs.supplier.example", "www.gov.uk"] }
FieldWhat it allows
fetchThe hosts web_fetch may read, by exact name, at most 32.
anytrue lets it read any public host instead. Say one or the other.
  • Never a private address. Every redirect is held to the same rule before it is followed, and so is where it lands.
  • A search goes to one provider. web_search asks the one agents.search names: brave, tavily, exa, serper, serpapi, kagi, perplexity or jina, or searxng, your own, at agents.search_url. None is set until somebody chooses, since a search is an agent's words sent to a third party. Its key is sealed as search-PROVIDER and sent only to that provider's host.
  • Both taint the run, since what comes back is somebody else's words. Once a run holds something private, an address it would read and a query it would send wait for a person, because either could carry it out (the breaker).
ToRun
Choose a search providerquilzo config set agents.search brave
Seal its keyquilzo secret set search-brave < key.txt
Search with your own SearXNGquilzo config set agents.search searxng, then quilzo config set agents.search_url https://search.example.org

An agent brought from another platform keeps these hands where they have an equivalent here: file-reading, grep, glob and edit tools come in as file_read, file_list, file_search and file_edit; a coding agent's web fetch and web search tools as web_fetch, reading any public host until you narrow fetch, and web_search; and a code interpreter as code_run, Python with no network.

Not yet

  • Credentials in commands. A secret handed into the box would be readable by whatever runs there, so a command that has to sign in to something is not offered one yet.
  • macOS and Windows hosts. The box is Linux's.
  • Long-running services and interactive programs. Commands and code run to the end with no terminal, which is what an agent needs; a terminal a person can take over comes later.
